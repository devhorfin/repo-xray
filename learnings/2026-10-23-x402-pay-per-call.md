# Putting a route behind x402 on Solana (REPO X-RAY slice 3)

## The problem, in one line
Charge $0.01 USDC per API call with no accounts or keys for the caller, on Solana, from a plain Node
server, without touching real money until the owner says so.

## The approach
1. Packages: `@x402/express`, `@x402/core`, `@x402/svm`, `@x402/fetch` (all v2.28.0, CommonJS works) plus
   `express` and `@solana/kit`. The older `x402`, `x402-express`, `x402-fetch` (1.x) are the v1 protocol with
   different header names; don't mix them.
2. Server: `new x402ResourceServer(new HTTPFacilitatorClient({ url })).register(SOLANA_DEVNET_CAIP2, new ExactSvmScheme())`
   from `@x402/svm/exact/server`, then `app.use(paymentMiddleware({ 'GET /api/v1/xray': { accepts: [{ scheme: 'exact',
   price: '$0.01', network, payTo }] } }, resourceServer))` before the route. `price: '$0.01'` becomes
   `amount: "10000"` of the network's default USDC (6 decimals); the 402 carries it base64-encoded in the
   `PAYMENT-REQUIRED` header with the facilitator's `feePayer`.
3. Facilitators: `https://x402.org/facilitator` serves `solana:EtWTRABZaYq6iMfeYKouRu166VU2xqa1` (devnet) for
   free; `https://facilitator.payai.network` serves mainnet `solana:5eykt4UsFv8P8NJdTREpY1vzqKqZKvdp`. Check
   `/supported` on either before relying on it. The Coinbase one wants an API key.
4. Client: `new x402Client().register('solana:*', new ExactSvmScheme(signer))` from `@x402/svm/exact/client`
   with `createKeyPairSignerFromBytes(Uint8Array.from(cliKeypairJson))`, wrapped by `wrapFetchWithPayment`.
   A `registerPolicy` filter caps what the client will ever pay (`amount <= 20_000n`).
5. The receiver needs a USDC token account before the first payment: the exact scheme calls
   `findAssociatedTokenPda` and never creates it. `setup-devnet.mjs` makes the receiver keypair and the account
   (`getCreateAssociatedTokenIdempotentInstruction` from `@solana-program/token`, paid by the devnet throwaway).
6. Dead end: `generateKeyPairSigner()` keys are not extractable (`InvalidAccessException` on `exportKey`), so
   a fresh keypair that must be saved comes from 32 random bytes and `createKeyPairSignerFromPrivateKeyBytes`.
7. Proof so far: bare request → 402 with the price; paying request → the client signs, the facilitator
   simulates and answers `invalid_exact_svm_transaction_simulation_failed` because the payer holds no devnet
   USDC. Everything up to the money is proven; the last step waits on Circle's faucet
   (faucet.circle.com, Solana Devnet) for wallet `GnrAZyuoXZBjC7yHfzVhB1Tp5jH5EHgmnZeUyvwaJNTg`.

## The judgment calls
- Devnet by default, mainnet behind a config switch (`XRAY_NETWORK=mainnet` + the owner's wallet). A paywall
  that takes real USDC is the owner's call ([[never-build-without-go]], money rule in CLAUDE.md).
- Did not use the faucet myself: it is a web form, and submitting forms needs the owner's say-so.
- Kept the free route and rate-limited it (10 an hour per address) instead of removing it. People use the
  page; bots use the paid route. The 429 message tells a bot where to go.
- Did not run a facilitator of our own. Verify/settle with a fee payer is the part that holds keys and
  needs uptime; the public ones exist for exactly this.

## The reusable rule
For an x402 route: v2 packages only, register the scheme for one CAIP-2 network on both sides, make sure
the receiver's token account exists before the first call, prove the 402 → sign → verify chain on a testnet
with a capped client policy, and leave mainnet as a config switch the owner flips.
